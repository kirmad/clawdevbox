Building Blocks

Triggers

Triggers make ClawDevbox proactive. A trigger is a small script that fires on a schedule, a webhook, or a manual poke; it polls whatever it needs, decides whether to act, and dispatches to an agent — no human in the loop required.

Type vs. registered instance

Trigger type

A capability shipped by a plugin or authored in a scope. Declares a script file, a parameter schema, a default cron, and (optionally) an identity param. A type doesn't fire on its own — it must be registered.

Registered instance

A concrete binding of a type to specific param values, with an optional cron override and an enabled flag. Instances live in .clawdevbox/triggers.json and are what the daemon actually ticks.

Firing modes

ModeHow it fires
cronThe in-process cron daemon ticks each registered instance on its cadence.
webhookAn external caller POSTs to the instance's /hooks/<id> endpoint.
manualtrigger.instance.fire (or the UI) — always works regardless of cron state.
testtrigger.test runs the script with a synthesized envelope, non-mutating.

The cron field on a registration is three-state: a string overrides the default, null inherits the type's default_cron, and false disables cron (manual / webhook still work).

The envelope contract

When a trigger fires, the script is handed a JSON envelope on stdin and is expected to observe, optionally dispatch, and always report its new state on stdout:

  1. Read stdin

    Parse the TriggerEnvelope — its config and lastFiredAt live on env.state; it also carries output_dir, a dispatch_url / spawn_url, and the CLAWDEVBOX_FIRE_SECRET bearer.

  2. Observe & decide

    Poll your source (ADO, the inbox, a metric, anything reachable). Write an observation.json under env.output_dir for the operator to inspect.

  3. Dispatch (optional)

    If there's work, POST to dispatch_url (wake / message an existing session) or spawn_url (start a new one), using Authorization: Bearer $CLAWDEVBOX_FIRE_SECRET.

  4. Emit state

    Print { "state": { … } } to stdout. The kernel persists state only by JSON-parsing stdout — this is how cooldown works.

The #1 trigger gotcha

Files written to output_dir are operator artifacts — the kernel does not read them back. State persists only through the {"state":{…}} JSON you emit on stdout. If you forget to re-emit lastFiredAt, your cooldown silently breaks and the trigger re-fires every tick.

Example trigger type

A minimal type declaration plus the registration that activates it:

# template.yaml — the TYPE (capability)
id: local.pr-comment-watcher
description: Watch a PR for new comments and dispatch a reply agent.
runtime: tsx
default_cron: "*/5 * * * *"      # every 5 minutes
identity_param: pr_id            # used to mint the registration id
accepts_webhook: true
parameters:
  - name: pr_id
    type: string
    required: true
// trigger.instance.register args — the INSTANCE
{
  "type_id": "local.pr-comment-watcher",
  "params": { "pr_id": "2401" },
  "cron": null,          // inherit default_cron (*/5 * * * *)
  "once": false
}

Authoring triggers

Prerequisite: read the authoring-triggers skill before writing any inline script — it codifies the envelope contract, state shape, cursor design, auth, and spawn routing. Skipping it produces subtle silent bugs (events never fire, state never advances).

  • Author a reusable type with trigger.template.create / trigger.template.update (ids must start with local.).
  • Register a concrete instance with trigger.instance.register — params are validated against the type schema.
  • Dry-run with trigger.test before relying on the cron path (it captures stdout, stderr, and any observation files without mutating state).

Registering a side-effecting trigger silently is an anti-pattern. Surface what you registered via the inbox so the user can see and disable it.
