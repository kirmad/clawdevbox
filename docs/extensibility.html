Extend & Integrate

Extensibility

ClawDevbox is built to be extended. Adding a capability is a drop-folder operation — a new recipe, skill, trigger, hostable tool, renderer, or CLI provider — never a code change to the host. This page is your map to every extension point.

Author a hostable tool

A hostable tool is the lightest way to add an MCP tool: a single TypeScript file in a plugin's tools/ directory that ClawDevbox loads into its own process. It exports an id, a description, a parameters zod schema, and an execute(args, ctx) function. 

import { z } from "zod";

export const id = "ado.get_pr_title";      // namespaced <plugin>.<verb>
export const description = "Fetch the title of an Azure DevOps pull request.";
export const parameters = z.object({
  pr_id: z.string().describe("The numeric PR id, as a string."),
});

export async function execute(args, ctx) {
  const pr = await ctx.http.get(
    `https://dev.azure.com/org/proj/_apis/git/pullrequests/${args.pr_id}`
  );
  return { title: pr.title, status: pr.status };
}
  • Ids must be namespaced — <plugin-name>.<verb> — so they never collide.
  • The tool becomes reachable through the meta-tool gateway like any built-in: learn_tool → run_tool.
  • ctx gives you the host's utilities (HTTP, config, secrets resolved from the keychain).

Reach for a hostable tool when a full external MCP server is overkill. Reach for an external MCP server (declared in mcpServers) when the integration is large, stateful, or already exists.

Author a custom renderer

A renderer turns an artifact folder into a browser view, dispatched on the artifact's type. Write a .mjs module that default-exports an object with a render(root, ctx) function. Drop it at .clawdevbox/renderers/<type>.mjs (workspace) or ship it in a plugin's renderers/. 

export default {
  type: "metrics-report",
  async render(root, ctx) {
    // ctx exposes helpers to read the artifact's files
    const data = await ctx.fetchFileJson("data.json");
    const rows = data.rows
      .map((r) => `<tr><td>${r.name}</td><td>${r.value}</td></tr>`)
      .join("");
    root.innerHTML = `<h1>${data.title}</h1><table>${rows}</table>`;
  },
};

Resolution is workspace → plugin → built-in, so a workspace renderer for an existing type shadows the built-in one. See Artifacts & Renderers for the built-in types.

Add a CLI provider

Want ClawDevbox to drive a different agent CLI? Declare it in your plugin manifest's clawdevbox.agent_clis[] and export a module with a spawnSession() entry point. The provider is responsible for launching the CLI inside the pty with the MCP config wired in. 

// my-provider.ts — referenced from clawdevbox.agent_clis[] in plugin.json
export const id = "my-cli";

export async function spawnSession(ctx, opts) {
  // ctx: paths, mcp config path, env; opts: model, prompt, resume id, ...
  return ctx.spawnPty({
    command: "my-cli",
    args: ["--mcp-config", ctx.mcpConfigPath, "--prompt", opts.prompt],
    env: { ...ctx.env },
  });
}

Once installed, the provider id can be used as a recipe's default_client or passed when beginning a recipe instance. Built-in providers are copilot, claude, and the echo-stub test provider.

Author a trigger template

To make something happen proactively, author a trigger type with trigger.template.create, then register concrete instances of it. Trigger scripts follow the stdin envelope contract (read config + state, observe, dispatch, emit new state on stdout).

Read the authoring-triggers skill first — it's the required reference for the envelope, state, cursor, and auth contract. Full details on the Triggers page.

Package it as a plugin

Any combination of the above becomes shareable when you list it in a plugin manifest's clawdevbox block. Then anyone can plugin.install from your git URL and pick up the whole set. The drop-folder philosophy holds end to end: your extension is just files, discovered and merged by scope — the host stays untouched.
